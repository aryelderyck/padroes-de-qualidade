# Mapa de arquivos do kit

Uma linha por arquivo do repositório: para que serve, por que está aqui e o que mais poderia ter sido feito.
Regra (`CONTEXTO.md`, seção 2, "Cada arquivo com o seu porquê", em teste no painel): todo arquivo é explicado **antes**
de ser criado, e esta tabela muda no mesmo commit que cria, move ou apaga um arquivo. Para conferir se falta alguém:
`git ls-files`. O `README.md` traz o índice curto e o mapa de consulta; aqui fica o porquê.

| Arquivo | Para que serve | Por que está aqui | Alternativas | Tarefa em que foi criado |
| --- | --- | --- | --- | --- |
| `.gitattributes` | Finais de linha LF em todo arquivo de texto, em qualquer sistema (regra 12 do `ERROS.md`) | Raiz, com esse nome, porque o git só procura esse nome e o da raiz vale para tudo | `core.autocrlf` em cada máquina (não viaja com o repositório); `.editorconfig` (só orienta editores, o git ignora); regras por extensão (mais longo, e `text=auto` já cobre) | Versão 0.4, durante o plano 1 do painel (`77fe5a8`) |
| `CHANGELOG.md` | O que mudou em cada versão do kit | Raiz, nome convencional que qualquer pessoa reconhece | Só o `git log` (mensagens soltas, sem agrupar por versão); GitHub Releases (fora do git e do link "raw" que os projetos leem) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `CONTEXTO.md` | Quem é a pessoa, como ensinar, mapa dos projetos, glossário, dificuldades e decisões | Raiz, porque vale para qualquer projeto; lido por seção, no começo de cada projeto | Dentro do `PADROES.md` (misturaria regras estáveis com contexto que muda toda semana); memória de um assistente (não é compartilhada entre ferramentas nem versionada) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `ERROS.md` | Catálogo de erros com causa raiz e índice; de consulta (as regras ficam no `REGRAS.md`) | Raiz, ao lado do `REGRAS.md`, que aponta para ele | Issues do GitHub (fora do git e fora do link "raw"); um arquivo por erro (mais difícil de ler as regras de uma vez) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `LICENSE` | Licença MIT: qualquer pessoa pode usar e adaptar o kit, mantendo o aviso | Raiz, onde o GitHub reconhece a licença | Sem licença (ninguém poderia reaproveitar legalmente); Creative Commons (pensada para texto, menos comum em repositório de código) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `PADROES.md` | Documento mestre: princípios, níveis, Definição de Pronto, testes, CI, segurança, LGPD, API, front-end, web pública, lições | Raiz; lido por seção, conforme o nível do projeto | Vários arquivos por assunto (mais links para seguir e mais difícil de ler inteiro pelo link "raw") | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `PRATICAS.md` | Caixa de entrada de práticas candidatas, com ciclo de vida até adotar ou descartar | Raiz, ao lado do `PADROES.md`, para separar o que é obrigatório do que está em teste | Seção "opcional" dentro do `PADROES.md` (confundiria regra com experimento) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `README.md` | Porta de entrada: o que tem no kit, em que momento abrir cada arquivo e como começar um projeto | Raiz, porque o GitHub mostra esse arquivo na página do repositório | Wiki do GitHub (fora do git); só este mapa (é longo demais para quem chega) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `REGRAS.md` | A única leitura de toda sessão: tabela "o que abrir, e quando", as 18 regras que saíram dos erros e o critério para registrar erro | Raiz, ao lado dos documentos que ele manda abrir; arquivo próprio e curto (limite de 80 linhas) porque é o único lido sempre | Deixar as regras dentro do `ERROS.md` (obrigava a abrir um arquivo de mais de 40 KB a cada sessão); repetir as regras no `CLAUDE.md` de cada projeto (cópias que ficam desatualizadas) | Versão 0.5 |
| `REVISAO-CRITICA.md` | Aviso de obsoleto (desde 2026-11-12), com o motivo e onde o conteúdo foi parar | Raiz, no mesmo nome, para quem chegar por um link antigo; o kit pede marcar como obsoleto em vez de apagar | Apagar o arquivo (links antigos quebrariam e a decisão ficaria só no histórico); manter os dois arquivos de perguntas (leitura e manutenção em dobro) | Primeiro commit do kit, versão 0.3 (`baf27e4`); obsoleto na versão 0.5 |
| `REVISAO.md` | Perguntas de revisão por momento (desenhar, escrever, otimizar, segurança, testes, entregar, aprender, comunicar, operar) | Raiz, citado pelo `REGRAS.md`, pelo `README.md` e pelo `CLAUDE.template.md`; recebeu em 2026-11-12 o que era só do `REVISAO-CRITICA.md` | Checklist dentro do `PADROES.md` (deixaria o mestre longo demais) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `docs/MAPA-DE-ARQUIVOS.md` | Este mapa: o porquê de cada arquivo | `docs/`, o mesmo caminho em todo repositório, para ser achado sempre no mesmo lugar | Raiz (combinaria com os documentos do kit, mas quebraria o caminho único); ampliar a tabela do `README.md` (a porta de entrada ficaria longa) | Versão 0.4, durante o plano 1 do painel |
| `templates/APRENDIZADOS.template.md` | Modelo do diário de aprendizado de cada projeto | `templates/` separa o que é **copiado** para os projetos do que é **lido** no kit; `.template` no nome evita confundir com um diário do próprio kit | Escrever do zero em cada projeto (cada um sairia num formato) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `templates/CHECKLIST-PRONTO.md` | Definição de Pronto por nível, com campo de evidência | `templates/`, porque é copiada para o `docs/` de cada projeto e marcada lá | Só a lista no `PADROES.md` (não teria onde marcar a evidência de cada projeto) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `templates/CLAUDE.template.md` | `CLAUDE.md` inicial de cada repositório novo, com o contexto da pessoa e as regras | `templates/`; o nome não é `CLAUDE.md` para o Claude Code não tratá-lo como instrução do próprio kit | `CLAUDE.md` na raiz do kit (seria lido como regra do kit, não como modelo) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `templates/Dockerfile.python` | Modelo de imagem Docker em múltiplos estágios, sem root (ainda não executado em projeto real) | `templates/`; o nome não é `Dockerfile` para o kit não parecer um projeto Docker | Escrever do zero em cada projeto (repetiria os mesmos cuidados de segurança, e algum ficaria de fora) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `templates/dockerignore` | Modelo de `.dockerignore` | `templates/`; sem o ponto inicial para não ser arquivo oculto nem ter efeito no kit | Deixar sem modelo (é fácil esquecer `.env` e `.git` e vazar segredo na imagem) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
| `templates/github/ci-node.yml` | Modelo de workflow de CI para projetos Node | `templates/github/` e não `.github/workflows/`, para não rodar no próprio kit | Copiar de um projeto antigo (traria configurações específicas dele) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |

| `templates/pyproject-python.toml` | Modelo de configuração de ruff, pytest e cobertura (ainda não executado em projeto real) | `templates/`; o nome não é `pyproject.toml` para o kit não parecer um pacote Python | `setup.cfg` ou arquivos separados por ferramenta (o `pyproject.toml` é o padrão atual e junta tudo) | Primeiro commit do kit, versão 0.3 (`baf27e4`) |
